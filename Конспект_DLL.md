# 📘 Конспект: динамические библиотеки и работа с файлами через отображение в память

## 1. Зачем нужна DLL, а не обычный файл с кодом

### 1.1. Что было бы без DLL

Представьте, что у вас 10 программ, и всем нужна функция «удалить пробелы из файла». Без DLL у вас два варианта:

- **Копировать код** в каждый проект → дублирование, баги чинятся в 10 местах.
- **Держать общий `.c`-файл** и подключать его в каждый проект → всё равно код вкомпилируется в каждый EXE, размер растёт.

### 1.2. Что даёт DLL

| Свойство | Объяснение |
|---|---|
| **Один код на диске** | Функция лежит в одном файле `Dll_var7.dll`, а не в 10 EXE. |
| **Одна копия в физической памяти** | Если 5 процессов загрузят одну DLL, Windows держит **один** экземпляр кода в RAM и проецирует его в адресные пространства всех процессов. Экономия памяти. |
| **Обновление без пересборки клиента** | Исправили баг в DLL → заменили `Dll_var7.dll` → все программы, которые её используют, получили фикс **без перекомпиляции**. |
| **Разделение труда** | Библиотеку может писать одна команда, программы — другая. |
| **Плагины** | Программа может во время работы решать, какую DLL загрузить (архитектура расширений — Photoshop, браузеры). |
| **Меньший размер EXE** | Клиент содержит только вызов, а не реализацию. |

### 1.3. Ключевое отличие DLL от «обычного файла с кодом»

Обычный `.c`-файл **вкомпилируется** в EXE на этапе сборки. Он **становится частью** исполняемого файла.  
DLL — **отдельный файл**, который подключается **во время выполнения**. EXE и DLL — это два разных PE-файла (Portable Executable), и связь между ними устанавливается через **таблицу экспорта** DLL и **таблицу импорта** EXE.

### 1.4. Внутреннее устройство DLL (коротко)

DLL — это тот же PE-формат, что и EXE. Внутри есть:
- **Таблица экспорта** — список имён функций, которые DLL отдаёт наружу (`ProcessFile`).
- **Точка входа `DllMain`** — вызывается системой при загрузке/выгрузке.
- **Секции кода, данных, ресурсов**.

Когда вы пишете `__declspec(dllexport) int ProcessFile(...)`, компилятор добавляет `ProcessFile` в таблицу экспорта. Когда клиент вызывает `GetProcAddress(hDll, "ProcessFile")`, Windows ищет это имя именно в этой таблице.

## 2. Клиентская часть: загрузка DLL и вызов функции

### 2.1. `LoadLibraryA` — загрузка библиотеки в память процесса

```c
HMODULE hDll = LoadLibraryA("Dll_var7.dll");
```

**Что делает:** открывает файл DLL, отображает его в **виртуальное адресное пространство** текущего процесса, вызывает `DllMain(DLL_PROCESS_ATTACH)`, возвращает **дескриптор модуля**.

**Почему `HMODULE`?** Это «handle module» — непрозрачный дескриптор. Фактически это адрес, по которому DLL загружена в память (база образа). Клиенту не нужно знать содержимое — он просто передаёт этот handle в другие функции.

**Почему `A`?** Суффикс означает ANSI-версию (однобайтовые строки `char*`). Есть `LoadLibraryW` — для `wchar_t*` (Unicode). Мы работаем с `char*`, поэтому `A`.

**Порядок поиска DLL (важно):**
1. Каталог, из которого запущен EXE.
2. Текущий каталог процесса.
3. Системный каталог Windows (`System32`).
4. Каталог Windows.
5. Каталоги из переменной `PATH`.

Поэтому мы кладём `Dll_var7.dll` **рядом с `App_var7.exe`** — чтобы п.1 сработал сразу.

**Счётчик ссылок:** каждая `LoadLibrary` увеличивает счётчик. `FreeLibrary` уменьшает. Когда счётчик = 0, DLL выгружается и вызывается `DllMain(DLL_PROCESS_DETACH)`.

### 2.2. `GetProcAddress` — поиск функции по имени

```c
ProcessFileFunc fn = (ProcessFileFunc)GetProcAddress(hDll, "ProcessFile");
```

**Что делает:** ищет в таблице экспорта DLL функцию с именем `"ProcessFile"` и возвращает её адрес в памяти процесса.

**Почему возвращает `FARPROC` (а не конкретный тип)?** Потому что `GetProcAddress` не знает сигнатуру функции — она может быть любой. `FARPROC` — это просто «указатель на функцию без типа». Мы **приводим** его к нужному типу сами.

### 2.3. `typedef` для указателя на функцию

```c
typedef int (*ProcessFileFunc)(const char*, const char*);
```

**Зачем:** чтобы компилятор знал сигнатуру. Без typedef пришлось бы писать `int (*fn)(const char*, const char*)` каждый раз. Typedef делает код читаемым.

**Синтаксис:** `int (*ProcessFileFunc)(...)` — «ProcessFileFunc — это указатель на функцию, принимающую (...) и возвращающую int».

### 2.4. Вызов и `FreeLibrary`

```c
int result = fn(argv[1], argv[2]);
FreeLibrary(hDll);
```

Вызов через указатель — точно такой же, как если бы функция была в самом EXE. `FreeLibrary` уменьшает счётчик ссылок; когда он обнулится, DLL выгрузится.

## 3. DLL-часть: экспорт функции

### 3.1. `__declspec(dllexport)`

```c
__declspec(dllexport) int ProcessFile(...)
```

**Microsoft-специфичный модификатор.** Говорит компилятору: «помести это имя в таблицу экспорта DLL». Без него функция будет видна только внутри DLL.

### 3.2. `extern "C"` — зачем нужно (в C++)

В C++ компилятор **искажает имена** (name mangling), чтобы различать перегрузки:
```cpp
int ProcessFile(const char*, const char*) 
// → ?ProcessFile@@YAHPEBD0@Z
```
Клиент, ищущий `"ProcessFile"`, ничего не найдёт.

`extern "C"` отключает искажение: имя остаётся `ProcessFile`.

**В нашем случае** файл `.c` компилируется как C — искажения нет и так. Но если бы файл был `.cpp`, `extern "C"` обязателен. Мы включили его «на всякий случай» — это стандартная практика.

## 4. Работа с файлами: обычный путь vs отображение в память

### 4.1. Обычное чтение (для сравнения)

```c
FILE* f = fopen("in.txt", "rb");
fread(buffer, 1, size, f);
// ... обработка ...
fwrite(buffer, 1, size, f2);
fclose(f);
```

Работает, но:
- Требует **явного буфера** в куче.
- Данные **копируются** из ядра → в буфер → обратно.
- Для больших файлов — двойные затраты памяти.

### 4.2. Отображение в память (наш подход)

**Идея:** сказать ОС: «сделай так, чтобы этот файл выглядел как массив байт в моём адресном пространстве». Тогда вы читаете файл **как обычную память** — без `read`, без копирования.

**Как это работает физически:**
1. Ядро создаёт объект «section» — общее представление файла.
2. При обращении к странице памяти, которой ещё нет в RAM, срабатывает **page fault** → ядро подгружает нужный блок файла с диска.
3. Программа «не замечает» — просто читает байты.

### 4.3. `CreateFileA` — открытие файла

```c
HANDLE hIn = CreateFileA(inputPath, GENERIC_READ, FILE_SHARE_READ, NULL,
                         OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);
```

Возвращает **дескриптор файла** — handle на объект ядра. Это не `FILE*` из stdio, а **низкоуровневый** handle Windows.

**Аргументы:**
| Аргумент | Значение | Почему так |
|---|---|---|
| `inputPath` | путь к файлу | — |
| `GENERIC_READ` | доступ на чтение | нам нужно только читать |
| `FILE_SHARE_READ` | разрешить другим тоже читать | иначе файл монопольно занят |
| `NULL` | атрибуты безопасности по умолчанию | не нужны |
| `OPEN_EXISTING` | открыть, только если существует | если нет — ошибка (наш код `-1`) |
| `FILE_ATTRIBUTE_NORMAL` | обычный файл | — |
| `NULL` | нет шаблона для создания | не нужно |

**Возврат:** `INVALID_HANDLE_VALUE` (= -1) при ошибке, иначе — handle.

### 4.4. `HANDLE` — что это

Это **не указатель** в обычном смысле. Это индекс в таблице объектов ядра текущего процесса. Через него ядро находит нужный объект (файл, mapping, поток). Закрывается `CloseHandle`.

### 4.5. `GetFileSize`

```c
DWORD size = GetFileSize(hIn, NULL);
```

Возвращает размер файла в байтах. `DWORD` — 32-битное беззнаковое (`unsigned long`). Для файлов >4 ГБ нужен второй параметр — старшие 32 бита. У нас `NULL` — считаем, что файл <4 ГБ.

**Почему важно:** нам нужно знать, сколько байт отображать в память.

### 4.6. `CreateFileMappingA` — создание объекта отображения

```c
HANDLE hMap = CreateFileMappingA(hIn, NULL, PAGE_READONLY, 0, 0, NULL);
```

**Смысл:** создаёт объект ядра «section», связанный с файлом. Пока ничего не отображается — только декларируется намерение.

**Аргументы:**
| Аргумент | Значение | Почему |
|---|---|---|
| `hIn` | handle файла | отображаем именно его |
| `NULL` | атрибуты безопасности | по умолчанию |
| `PAGE_READONLY` | только чтение | мы не будем писать в исходный файл |
| `0, 0` | размер = весь файл | 0 означает «до конца» |
| `NULL` | имя объекта | не нужно (без имени) |

**Возврат:** handle объекта mapping.

### 4.7. `MapViewOfFile` — отображение в адресное пространство

```c
char* src = (char*)MapViewOfFile(hMap, FILE_MAP_READ, 0, 0, 0);
```

**Смысл:** теперь ядро выделяет диапазон в **виртуальной памяти процесса** и говорит: «адреса в этом диапазоне соответствуют байтам файла».

**Аргументы:**
| Аргумент | Значение | Почему |
|---|---|---|
| `hMap` | handle mapping | что отображаем |
| `FILE_MAP_READ` | доступ на чтение | — |
| `0, 0` | смещение = 0 | с начала файла |
| `0` | размер = весь | 0 = до конца |

**Возврат:** указатель `LPVOID` на начало отображения. Приводим к `char*`, чтобы читать байты.

**Ключевой момент:** теперь `src[i]` — это **чтение байта № i из файла**. Без `ReadFile`, без буфера, без копирования в кучу (копирование произойдёт неявно ядром по страницам).

### 4.8. Обработка: удаление пробелов

```c
char* dst = (char*)malloc(size);
int removed = 0, pos = 0;
for (DWORD i = 0; i < size; i++) {
    if (src[i] == ' ') removed++;
    else dst[pos++] = src[i];
}
```

- **Читаем** из `src` (это файл в памяти).
- **Пишем** в `dst` (обычная куча).
- `removed` — счётчик удалённых пробелов.
- `pos` — сколько байт уже записано в результат.

**Почему не пишем прямо в `src`?** Потому что `PAGE_READONLY` — запись приведёт к нарушению доступа. Плюс мы не хотим менять исходный файл.

### 4.9. Освобождение ресурсов отображения

```c
UnmapViewOfFile(src);
CloseHandle(hMap);
CloseHandle(hIn);
```

**Порядок важен:**
1. Сначала снимаем отображение (иначе handle mapping останется «занятым»).
2. Затем закрываем mapping.
3. Затем — файл.

Если перепутать — `CloseHandle` вернёт ошибку.

### 4.10. `WriteFile` — запись результата

```c
HANDLE hOut = CreateFileA(outputPath, GENERIC_WRITE, 0, NULL,
                          CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, NULL);
WriteFile(hOut, dst, pos, &written, NULL);
```

**Аргументы `CreateFileA` для выходного файла:**
| Аргумент | Значение | Почему |
|---|---|---|
| `GENERIC_WRITE` | доступ на запись | — |
| `0` | никому не давать доступ | файл монопольно наш |
| `CREATE_ALWAYS` | создать или перезаписать | старый файл не нужен |

**`WriteFile`:**
| Аргумент | Значение |
|---|---|
| `hOut` | куда пишем |
| `dst` | откуда (наш буфер) |
| `pos` | сколько байт (без пробелов!) |
| `&written` | сюда ОС запишет реально записанное количество |
| `NULL` | для асинхронного I/O, не нужно |

**Проверка:** `written == pos` — если нет, запись неполная → код `-6`.

## 5. Почему именно такие аргументы функции `ProcessFile`

```c
int ProcessFile(const char* inputPath, const char* outputPath)
```

| Часть | Смысл |
|---|---|
| `int` (возврат) | >0 — количество удалённых пробелов, <0 — код ошибки. Один int — и результат, и признак ошибки. |
| `const char* inputPath` | Путь к входному файлу. `const` = «функция не будет менять строку». `char*` — ANSI-строка. |
| `const char* outputPath` | Путь к выходному файлу. |

**Почему не передаём размер файла?** Потому что функция сама его узнаёт (`GetFileSize`). Клиент не должен об этом думать.

**Почему не открываем файлы в клиенте?** Потому что тогда клиент был бы привязан к Windows API. Мы хотим, чтобы DLL **инкапсулировала** всю логику: «дай пути — получи результат».

## 6. Обработка ошибок: почему коды отрицательные

| Код | Где | Что |
|---|---|---|
| `-1` | `CreateFileA` (input) | файл не найден / нет доступа |
| `-2` | `GetFileSize` | не удалось получить размер |
| `-3` | `CreateFileMappingA` | не удалось создать отображение |
| `-4` | `MapViewOfFile` | не удалось отобразить |
| `-5` | `malloc` или `CreateFileA` (output) | нет памяти / не создать файл |
| `-6` | `WriteFile` | ошибка записи |

**Почему не `GetLastError()`?** Потому что `GetLastError` живёт **только в текущем потоке** и может быть перезаписан любым следующим вызовом API. Надёжнее вернуть свой код, а клиент сам решит, что с ним делать.

**Положительные значения** — количество удалённых пробелов. Если их 0, вернётся 0 — что тоже «успех».

## 7. Схема целиком

```
┌─────────────────────────────┐         ┌──────────────────────────────┐
│ App_var7.exe                │         │ Dll_var7.dll                 │
│                             │         │                              │
│ 1. LoadLibraryA ────────────┼────────►│ (Windows грузит DLL в RAM)   │
│                             │         │                              │
│ 2. GetProcAddress("ProcessFile") ────►│ ищет в таблице экспорта      │
│                             │         │                              │
│ 3. fn("in.txt","out.txt") ──┼────────►│ ProcessFile:                 │
│                             │         │  CreateFileA(input)          │
│                             │         │  GetFileSize                 │
│                             │         │  CreateFileMappingA          │
│                             │         │  MapViewOfFile               │
│                             │         │  цикл: убрать пробелы        │
│                             │         │  UnmapViewOfFile             │
│                             │         │  CloseHandle × 2             │
│                             │         │  CreateFileA(output)         │
│                             │         │  WriteFile                   │
│                             │         │  CloseHandle                 │
│                             │◄────────┤ return removed               │
│ 4. printf("%d", result)     │         │                              │
│                             │         │                              │
│ 5. FreeLibrary ─────────────┼────────►│ (Windows выгружает DLL)      │
└─────────────────────────────┘         └──────────────────────────────┘
```

## 8. Что важно запомнить на будущее

1. **DLL = отдельный PE-файл** с таблицей экспорта. Загружается во время выполнения.
2. **`LoadLibrary` → `GetProcAddress` → вызов → `FreeLibrary`** — канонический цикл динамической загрузки.
3. **`__declspec(dllexport)`** — что отдать наружу; **`__declspec(dllimport)`** (для статической линковки) — что взять.
4. **Отображение в память** даёт «файл как массив байт» — быстро, без явного чтения.
5. **Handle** — дескриптор объекта ядра, закрывается `CloseHandle`.
6. **Отрицательные коды** — соглашение об ошибках, надёжнее `GetLastError`.
7. **Порядок освобождения** ресурсов: view → mapping → file.
